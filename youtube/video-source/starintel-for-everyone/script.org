* Cold open — 0:00–0:35

[VISUAL: black screen. Three browser tabs pop in: a search result, a PDF, a
social post. Smash cut to a dense Quasar graph.]

Search is great at finding pages.

It is terrible at remembering what those pages meant together.

You open twenty tabs. You copy a few notes. You lose which claim came from
which source. Then tomorrow you start over.

StarIntel is my attempt to fix that.

Instead of treating the web like a pile of tabs, it turns what you collect into
typed documents, keeps the sources attached, links related records, and lets
small workers — actors — keep expanding the graph.

And I am not going to explain it with a fake animation.

I am going to install the public stack, run it, fire a real actor, inspect real
Auto Dig data, and finish inside Quasar.

[ON SCREEN TEXT: "public repos · localhost · live demo"]

* The one-minute mental model — 0:35–1:30

[VISUAL: dslide with DOCUMENTS → ACTORS → GRAPH]

There are only three ideas you need.

First: *documents*.

A StarIntel document is a record with a type, an ID, a dataset, timestamps,
data, and room for sources, evidence, provenance, relations, and other metadata.

That sounds boring. Boring is good. Boring means a result can move between
tools without becoming mystery JSON.

Second: *actors*.

An actor is a worker that consumes a target or a document and can emit more
documents or relations. One actor can normalize something. Another can fetch a
public source. Another can enrich a record. They do not all need to live in one
process.

Third: *Quasar*.

Quasar is the operator surface. The graph you see is a projection of the
documents. It is not the evidence itself. You can click through the records,
inspect them, search them, and operate the system.

[BEAT]

Documents are the memory.

Actors do the repetitive work.

Quasar is where a human drives.

* Install the public StarIntel stack — 1:30–3:05

[VISUAL: terminal, large font. Keep command history visible.]

I am starting from the public StarIntel Server repository.

#+begin_src sh
git clone https://github.com/lost-rob0t/starintel-server
cd starintel-server
cp .env.example .env
#+end_src

The local stack is Nix-built and Docker-run. CouchDB stores documents. RabbitMQ
moves messages. Valkey handles runtime coordination. The Lisp server owns the
StarIntel HTTP and actor-routing layer.

This is a development stack, so I keep every service on localhost.

[VISUAL: fast cut while secret files are generated; do not expose values.]

#+begin_src sh
install -d -m 0700 secrets
openssl rand -base64 32 > secrets/couchdb_password
openssl rand -base64 48 > secrets/couchdb_secret
openssl rand -hex 24 | tr '[:lower:]' '[:upper:]' > secrets/erlang_cookie
openssl rand -base64 32 > secrets/rabbitmq_password
openssl rand -base64 32 > secrets/valkey_password
openssl rand -base64 48 > secrets/auth_pepper
openssl rand -base64 48 > secrets/auth_bootstrap_secret
chmod 0600 secrets/*
#+end_src

Then build and load the project images and start the stack.

#+begin_src sh
nix run .#load-images
docker compose up --detach --wait
curl --fail http://127.0.0.1:5000/health
#+end_src

[VISUAL: CAPTURE LIVE health response. Do not pre-render output.]

If this health check does not pass during rehearsal, this shot does not go in
the video.

Now I bootstrap one local administrator credential.

#+begin_src sh
bootstrap_secret="$(<secrets/auth_bootstrap_secret)"

curl --fail --silent --show-error \
  --request POST \
  --header 'Content-Type: application/json' \
  --header "X-Star-Bootstrap-Secret: $bootstrap_secret" \
  --data '{"owner":"youtube-demo"}' \
  --output /tmp/starintel-bootstrap.json \
  http://127.0.0.1:5000/auth/bootstrap

api_key="$(jq --exit-status -r '.api_key' /tmp/starintel-bootstrap.json)"
test -n "$api_key"
printf 'local StarIntel credential created\n'
#+end_src

[PRODUCTION: the bootstrap response is written to a file; do not open it on
screen. The credential never needs to be visible.]

And now I can ask the server who I am.

#+begin_src sh
curl --fail --silent \
  --header "Authorization: Bearer $api_key" \
  http://127.0.0.1:5000/auth/context |
  jq '{principal_id, principal_type, owner}'
#+end_src

[VISUAL: CAPTURE LIVE. Zoom only the principal type/owner fields.]

* Run a public actor — 3:05–4:40

[VISUAL: switch to Quasar UI.]

I am using Quasar's public browser actor runtime for the first demo because it
is easy to reproduce and the exact flow is covered by the project's end-to-end
tests.

From the public Quasar UI repository:

#+begin_src sh
git clone https://github.com/lost-rob0t/quasar-ui
cd quasar-ui
npm ci
npm run dev
#+end_src

[VISUAL: open the local Vite URL shown by the command.]

In Settings, actor execution is opt-in. I enable it.

Then I create a target with the built-in actor:

#+begin_example
actor  = quasar.actor.target-input-expansion
target = https://example.com/research
#+end_example

This is deliberately harmless demo input.

[VISUAL: create the target in the UI. Then cut immediately to resulting graph.]

The actor classifies the target and returns a declarative transform plan. Quasar
validates that plan and applies it through the normal operation path.

The useful part is what happens next: the URL is not just text in a textbox.
It becomes a typed record that the rest of the system can address.

[VISUAL: click the generated node. Show ID, dtype, dataset/data, and relation.]

That is the actor model in miniature.

Input comes in.

A worker transforms it.

New documents and relationships become visible.

And the original record remains inspectable.

* Why the graph matters — 4:40–5:45

[VISUAL: pan across graph; select a node, inspect document, traverse relation.]

The graph is where this stops feeling like a database demo.

A normal search result gives me a page.

A StarIntel record can have a stable identity, sources, evidence, time,
geography, and explicit relations to other records.

That means I can ask different questions later without recollecting the same
thing from scratch.

What is connected to this source?

What changed?

Which records came from the same observation?

Which event has geography?

Which document has no source yet?

Which actor produced this relation?

The important rule is that the graph itself is not proof.

An edge on screen should point back to the documents and provenance that justify
it.

That is why I care about keeping the boring metadata.

* GPT Auto Dig — 5:45–7:15

[VISUAL: terminal in public =starintel-gpt-auto-dig= checkout.]

Now for the research side.

GPT Auto Dig is public too. At its core it is an evidence-first research corpus:
Git-backed StarIntel documents plus tooling to validate, search, and render
them.

#+begin_src sh
git clone https://github.com/lost-rob0t/starintel-gpt-auto-dig
cd starintel-gpt-auto-dig

git clone https://github.com/lost-rob0t/starintel-doc.nim .starintel-doc-nim
nimble buildFast
nimble validate
#+end_src

[VISUAL: CAPTURE LIVE validator summary.]

The validator checks the document contract and source-reference shapes. It also
writes an =unverifed= report for records that have empty source arrays.

That distinction matters.

A record existing in the graph does not magically make it true.

Now I search the public corpus.

#+begin_src sh

* The full loop — 7:15–8:25

[VISUAL: dslide showing TARGET → ACTOR → DOCUMENTS → RELATIONS → QUASAR →
NEW TARGETS.]

Now put the pieces together.

A human or another system creates a target.

An actor accepts work.

The actor emits StarIntel documents and relations.

Those records are stored and routed.

Quasar projects them into a graph a human can operate.

Research data such as Auto Dig packets can use the same document model.

And new targets can be created from what you learned.

That is the loop.

It is not "AI searches the internet and tells you the answer."

It is closer to an evidence operating system where automation can do more of
the repetitive collection and transformation, while the records stay visible
enough for you to challenge them.

* Why this is useful outside OSINT nerd land — 8:25–9:30

[VISUAL: quick cards: city meeting → event docs; company → sources/relations;
software project → changes/docs; research topic → evidence graph.]

You do not have to care about intelligence jargon to want this.

A journalist can keep claims attached to sources.

A researcher can stop losing provenance between tools.

A developer can build one actor without rebuilding the whole pipeline.

A civic-data nerd can collect public meetings and connect them to places,
organizations, and documents.

A team can keep machine-generated work inspectable instead of burying it in
chat history.

And because the core pieces are ordinary software — Git repositories, typed
documents, services, actors, a graph UI — you can inspect the implementation
while it runs.

That is the sell.

Not "trust the AI."

Trust less.

Keep more evidence.

Make the machinery inspectable.

* What is still rough — 9:30–10:05

[VISUAL: simple "experimental" slide, then GitHub issue/commit montage.]

StarIntel is still experimental.

Some actor implementations are private.

Some server paths still have legacy compatibility code.

The full Quasar runtime is heavier than the standalone UI.

And a development stack is not the same thing as a hardened public service.

I would rather show you those boundaries than fake polish that is not there
yet.

The public repos are moving fast, and the video description should link the
exact revisions used for this recording.

[VISUAL: Quasar graph. Slowly zoom out.]

If this idea clicks for you, do one thing.

Clone the public repos.

Do not start with "AI that knows everything."

That is how the graph becomes useful.
