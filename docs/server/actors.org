StarIntel Server's concurrency model combines three layers:

- *Sento actors* for local concurrency, supervision boundaries, timers, and
  message passing.
- *RabbitMQ topic exchanges* for document and actor traffic across process
  boundaries.
- *CouchDB* as the durable store every actor's output eventually lands in.

* Local versus remote delivery

When a document event fires, the runtime can deliver work two ways:

1. *Local actor via TELL* — in-process message passing under Sento
   supervision. Fast, same failure domain.
2. *Remote actor via RabbitMQ topic route* — crosses the exchange so another
   service (or another host's collector) consumes it under its own
   supervision.

Both paths exist so a crashing consumer is isolated rather than fatal.
Derived documents re-enter through the ingest exchange — see
[[id:docs-server-ingest][ingest and dataflow recursion]] for why that recursion is durable.

* Why supervision matters

The jobs are real-world flaky: networks die, providers rate-limit, parsers
crash on malformed input, queues back up. A supervised runtime restarts or
isolates pieces instead of taking the investigation down. This is the
platform-level argument from [[id:intro-what-is-starintel][What Is StarIntel]] — actors everywhere, one
document model — implemented on the server as Sento boundaries plus exchange
routing.
