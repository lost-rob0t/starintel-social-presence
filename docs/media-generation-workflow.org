* What media-gen is

=media-gen= is a SWI-Prolog application built on =prolog-rlm=.

The canonical path is:

#+begin_example
Emacs
  -> media-gen
  -> Prolog-RLM
       -> rlm_graph
       -> rlm_async
       -> rlm_chain / artifacts / authority as required
  -> media providers
#+end_example

Python is not the media-gen application runtime.

The current executable slice intentionally stops before paid live media calls. It proves the deterministic expert, character resolution, provider-neutral request boundary, asynchronous Future execution, durable graph interrupt/resume, Org production template, and Emacs/comint integration with a fake provider that uses the same generic API.

The returned decision contains the reference class, matched canonical characters, provider/model configuration, stable expert branches, reason, and confidence.

Concrete model identifiers are configuration. Expert rules choose the provider/capability route rather than treating a mutable model ID as permanent truth.

The current built-in catalog is a small fixture-quality seed, not the final mega catalog. The large Wikidata/Wikimedia-backed catalog remains follow-up work and should be loaded/queryable from Prolog rather than requiring the retired Python application layer.

* 6. Generic async media API

The reusable provider-neutral layer lives under:

#+begin_example
prolog/media/
#+end_example

It contains no StarIntel, Emacs, or publishing assumptions.

Conceptually:

#+begin_src prolog
image_generate_async(Request, Future).
video_generate_async(Request, Future).
voice_generate_async(Request, Future).
#+end_src

The implementation direction is:

#+begin_example
canonical execute predicate
  -> rlm_async Future
  -> optional caller await
#+end_example

The deterministic fake provider supports image, video, and voice request shapes so orchestration can be tested without credentials or cost.

* 7. Durable media graph

The first real =rlm_graph= workflow is:

#+begin_example
expert_plan
  -> compile_context
  -> compile_request
  -> generate_keyframe
  -> human_review
       INTERRUPT
  -> resume
  -> finalize
#+end_example

The human review stage returns an actual graph interrupt. The graph Future completes in a paused state; no async scheduler worker sits around waiting for a person.

Resume continues the same run from its checkpoint.

This is the foundation for later image approval -> voice -> remote video submit -> persistent poll -> QA -> publish-plan graphs.

* 10. Paid-provider boundary

Normal CI does not generate paid media.

Before adding a live provider adapter:

1. verify the provider's current official API;
2. implement it behind the generic Prolog media request boundary;
3. keep the async execute -> Future direction;
4. pass actual input assets when the provider supports them;
5. normalize provider errors structurally;
6. add deterministic fake/offline coverage first;
7. keep paid smoke tests explicit and manual.

Do not resurrect a Python provider orchestrator merely because an SDK example is written in Python.

* 11. External-effect identity

Long-running and paid effects must not be duplicated by Prolog backtracking, retries, repeated waits, callbacks, or process restart.

The general reusable once-only effect ledger is tracked upstream in =prolog-rlm= issue #57 at the time of this slice.

media-gen must not create a competing generic effect runtime. Paid/retry-sensitive provider work should reuse the upstream mechanism when it lands, or remain bounded behind explicit deterministic semantics until that dependency is ready.
