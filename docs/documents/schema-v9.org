StarIntel consumers do not all select the same document release. This page
describes the v0.9 contract selected by the main-site consumer lock in
=starintel-labs/website/packages/starintel-doc/schemas/starintel-schema.lock.json=.
That lock records *release/profile 0.9.1* and *base schema 0.9.0*.

Those numbers describe different things. The release profile identifies the
consumer contract, while the base schema identifies the immutable wire-schema
family. A consumer can therefore use release 0.9.1 while continuing to
validate documents against the 0.9.0 base schema and its additive profile.

* What the contract provides

The contract gives producers and consumers a shared structure for typed
documents, including their identity, dataset, sources, evidence, and
assessment. Type-specific fields are checked against the selected schema.
Consumers pin the lock and validate against that exact contract instead of
choosing a version from a filename or a documentation title.

For the StarIntel v0.9 family:

- The website lock selects release/profile =0.9.1=.
- The same lock identifies base schema =0.9.0=.
- The immutable schema filename remains =starintel-doc-v0.9.0.schema.json=.
- Additive profile changes do not rename or replace that base schema.

* Why another page mentions 0.10.1

StarLang 0.10.1 is a separate contract used by the Auto Dig findings adapter.
It is not the release selected by the website's v0.9 lock. The adapter page
describes that consumer and its own version boundary:

- [[https://docs.starintel.actor/documents/star-lang-0.10.1.html][StarLang 0.10.1 findings-adapter input]]

Keep the consumer and its lock beside every version claim. The string
=0.10.1= is not a replacement for the website's pinned v0.9 profile.

The lock's canonical source is
=lost-rob0t/starintel-gpt-auto-dig@6479c0a9dc88ce9fed183515fc4df5d245de0b3a=.

* Compatibility rules

- Validate with the consumer's pinned lock.
- Keep =release_version= distinct from =schema_version=.
- Treat schema filenames as immutable artifact names, not release selectors.
- Make migrations explicit; do not relabel old records to pass validation.
- Keep source, evidence, and uncertainty attached to derived conclusions.
