* Historical compatibility—not a new-producer starting point

This URL is retained for readers handling historical v0.9 records. The current
Server and MCP source pins used by these tutorials select release/base 0.10.1
from StarLang. The website's current consumer lock also selects 0.10.1; the
older statement that its active release was v0.9 is no longer current.

Start new workflows with [[file:star-lang-0.10.1.org][the current document-shape guide]] and the
actual consuming repository's lock. A document's version, an API client's
package version and a deployed server's version are not interchangeable.

* Preserve the historical contract

In the additive v0.9 family, a release/profile could advance while its immutable
base-schema version and filename remained unchanged. That is why a v0.9.0
filename cannot tell you which release a consumer selected.

- Resolve =release_version= and =schema_version= from the relevant consumer lock.
- Follow its canonical repository/commit and run its native checker.
- Keep explicitly historical records on their documented compatibility path.
- Do not rename =_id= to =id= or edit =schemaVersion= merely to pass validation.
- Migrate through an explicit supported migration and validate the result.

Some actor families still have explicit historical boundaries while others use
the canonical SDK. Check the selected actor's guide; never feed every worker
the same arbitrary schema file. See [[file:../tutorials/actors.org][Pro actors]].
