* Current tutorial contract

The source pins used by these tutorials resolve StarIntel release/base 0.10.1
from StarLang. Server and MCP pin different canonical commits of that release;
each consumer's generated artifacts and hashes remain its own authority.
Never assume all projects select the same commit just because version strings match.

For a consumer with =schema/starintel-schema.lock.json=, read =release_version=,
=schema_version=, =canonical_repository= and =canonical_commit=, then run that
repository's native checker. Do not infer current authority from README text,
a schema filename or a historical issue.

* Flat record shape

Canonical records use lowerCamelCase fields at the document root. Identity,
dataset, document kind and version use =id=, =dataset=, =dtype= and
=schemaVersion=. The selected dtype defines its own additional required fields.
Do not invent a =data= envelope or copy a historical =_id= example as a new record.

The local engine can build/validate the canonical envelope from a small
dtype-specific input, as demonstrated in [[file:../tutorials/cli.org][the CLI tutorial]]. An input
snippet such as ={"rawContent":"Synthetic training note"}= for dtype =document= is not, by itself, a
complete portable StarIntel record. Export the validated result when exchanging
documents, and check the receiving consumer's lock/capabilities.

* Generated validation and numeric precision

Use the pinned generated schema/runtime rather than a hand-maintained duplicate
field registry. The maintained Python client uses the canonical JSON codec to
preserve exact JSON numbers. When re-encoding client responses that contain
exact decimals, use =starintel_canonical.stringify_json= rather than silently
converting through binary floating point.

The findings adapter in this repository is read-only. It validates canonical
flat records through its pinned =starintel-doc= dependency and retains source
paths, IDs, dtype, dataset and references. It does not treat graph adjacency as
proof of an association. See [[file:../desk/findings.org][the findings adapter]].

* Explicit compatibility

Historical records retain their historical version and read-only/compatibility
path where supported. [[file:schema-v9.org][The v0.9 guide]] explains the release/base distinction.
Never relabel old data to bypass validation or assume server acceptance implies
every actor can consume it.
