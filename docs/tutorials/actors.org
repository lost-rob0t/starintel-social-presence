* What an actor does—and what this exercise will not do

Pro actors collect or enrich material and return StarIntel documents. Python
workers run with Pykka; optional Common Lisp plugins run inside Star Server.
The server owns recurring targets, leases, fencing, retries and recovery.
Workers are not a second scheduler and must not write directly to CouchDB.

This tutorial walks from installing an authorized fleet checkout to reviewing a
one-shot request, starting one worker and checking the execution chain. Live
collection requires permission for the source, an approved target and any
provider credentials. No live scrape is silently performed by the offline steps.

Prerequisites:

- A working server and RabbitMQ, as in [[file:local-install.org][the local-install tutorial]].
- Access to the actor fleet checkout/package supplied by your administrator.
  It is separately distributed; a server API key does not grant source access.
- Access to its lock-pinned dependencies as well. The fleet currently fetches
  some SDK/client dependencies over GitHub HTTPS; Forgejo SSH access alone does
  not guarantee those installs work. Resolve package access with your operator.
- Python 3.12+, Git and the native/browser dependencies of your selected actor.
- A broker account for the intended exchange/vhost and an API key authorized
  for the target operation and dataset. These are different credentials.

* 1. Choose the correct actor surface

Every advertised actor has a manifest describing its service mode and a
scriptable =sa-<actor-id>= executable. The executable name fixes actor identity;
do not pass another actor ID as the first positional argument.

| Service mode | Continuous runtime | One-shot behavior |
|--------------+--------------------+-------------------|
| Target consumer | Shared RabbitMQ transport | Print or submit a target request |
| Document stream | Continuous document consumer | Transform JSONL from stdin/file |
| Server plugin | Common Lisp host inside Star Server | Submit a target; do not start another Lisp server |

For example, =sa-user-hunt= builds a target request; =sa-watchlist= consumes
documents using an explicit rules file. They do not have the same arguments.
Use manifests and the installed commands' =--help= as the inventory authority,
not an old README's hard-coded actor count.

* 2. Install the authorized fleet

Set =ACTOR_FLEET_DIR= to the actual authorized checkout path. From its root:

#+begin_src sh
cd "$ACTOR_FLEET_DIR"
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e . -e './python[dev,amqp,server]'
starintel-actor-service list
starintel-actor-manifests --help
sa-user-hunt --help
#+end_src

The root mapping package and Python fleet package are both needed. The =amqp=
extra installs broker publication dependencies; =server= installs the maintained
HTTP client for explicit submission. Actor-specific provider extras and browser
installation remain separate. Do not install every credentialed collector just
to run a username-generation or synthetic test.

For Nix users, the authorized fleet's =nix develop= supplies its native/runtime
environment. The source's own install guide lists per-output builds. Do not
assume entering a shell installs every executable globally.

* 3. Review an offline target request

First remove the implicit actor-server URL from this shell so omission of
=--server= cannot accidentally submit through an inherited environment variable:

#+begin_src sh
unset STARINTEL_SERVER_URL
sa-user-hunt intro_example_not_a_real_account \
  --dataset training --once --delay 1 \
  --idempotency-key intro-user-hunt-001 > request.json
python -m json.tool request.json
#+end_src

With no server configured, this emits deterministic =targets.create= request
JSON and does not contact providers. Review the actor, dataset, target, cadence
and options. This is a request body, not proof of a registered actor or completed
collection. Treat files with real selectors/targets as private operational state.

For actor-specific options, use repeated =--option KEY=JSON= values. Quote JSON
strings, arrays and objects correctly. Never place provider tokens directly in
options; use the documented runtime credential reference instead.

* 4. Verify server capabilities and actor registration

With the server URL and API key loaded according to [[file:api-keys.org][the API-key tutorial]],
use the maintained Python client in a separate client environment:

#+begin_src python
import os
from starintel_client import StarIntelClient

with StarIntelClient(os.environ["STAR_SERVER_URL"],
                     api_key=os.environ["STARINTEL_API_KEY"]) as client:
    registry = client.discover()
    print("targets.create available:", registry.has_operation("targets.create"))
    for op in registry.operations:
        if "actor" in op.operation_id or op.operation_id == "targets.create":
            print(op.operation_id, op.scopes)
    if registry.has_operation("actors.list"):
        print(client.call("actors.list").data)
#+end_src

Use the catalog operation actually advertised by your server to inspect actor
manifests and bounded availability. =actors:read= can discover actors but cannot
invoke them. A locally installed executable, a manifest document and a healthy
continuous worker are separate facts. Resolve any missing capability before
submitting work; do not use a legacy target route as a fallback.

* Registration boundary: operator-provisioned, not automatic

For the pinned versions, starting a Python worker and publishing its document-
shaped fleet manifest do *not* automatically populate the server's trusted
actor catalog. The server registry expects its own validated manifest boundary
(including =resourceUri=, =semantic= and provenance), installed through trusted
server configuration/registration. The fleet's =actor-manifest= document is a
different shape, not a drop-in registration call.

Have the server operator provision the supported registration/adapter for your
chosen actor and verify it with =actors.list= before continuing. On a fresh
local backend without that adapter, this step is an explicit integration
blocker: you can finish the offline request and local document exercises, but
must not claim live dispatch is configured. Do not work around it by inventing
a route or copying private init code from an unrelated deployment.

The verification code above prints the actual catalog when =actors.list= is
advertised. Ask the operator to confirm the exact actor identity, semantic
capability, source revision and availability; a =service.started= transport
event alone is not proof of registry admission. Once provisioned, the remaining
steps demonstrate the worker and approved-target lifecycle.

* 5. Start exactly one continuous worker

This example chooses =user-hunt=, which uses the pinned canonical SDK and must
not be given a legacy =--schema=. Configure a private broker connection:

#+begin_src bash
export RABBITMQ_HOST=127.0.0.1
export RABBITMQ_PORT=5672
export RABBITMQ_VHOST=/
export RABBITMQ_USER=starintel
read -r -s -p 'Broker password: ' RABBITMQ_PASSWORD
echo
export RABBITMQ_PASSWORD
starintel-actor-service user-hunt
#+end_src

Run it in a dedicated terminal/service under your chosen supervision. Use the
operator-issued broker password; the API key is not that password. The canonical
service boundary selects its SDK automatically. Other actor families may
explicitly require a compatibility schema artifact or provider credentials;
follow the selected actor's guide rather than supplying an arbitrary schema.

The Python fleet's Compose stack can run managed workers too, but it has its
own broker setup. Do not accidentally start a second isolated broker and then
send server targets to the first one. Align exchange, vhost, credentials and
network routing. In a container, =127.0.0.1= means that container, not the host.

* 6. Submit only an approved target

Replace the training selector only after obtaining source authorization and
reviewing the actor's behavior, provider limits and allowed dataset. This command
is a real server request and can trigger collection:

#+begin_src sh
sa-user-hunt "$APPROVED_USERNAME" --dataset "$APPROVED_DATASET" \
  --once --delay 1 --idempotency-key "$APPROVED_REQUEST_ID" \
  --server "$STAR_SERVER_URL"
#+end_src

=STARINTEL_API_KEY= supplies the bearer credential. The maintained client
discovers =targets.create= and fails if unavailable. An idempotency key identifies
the intended logical request; do not reuse one for different targets. Start with
=--once=; recurring schedules require an explicit cadence and operational owner.

* 7. Verify the complete chain

Check each boundary independently:

1. HTTP receipt: the target request was accepted; retain its correlation ID.
2. Server state: the target exists in the intended dataset and is eligible.
3. Dispatch: Star Server routes the remote target over the =documents= exchange
   using =documents.target.dispatch.<actor>=.
4. Consumption: the worker receives/validates it and performs the authorized work.
5. Publication: output returns through =documents.ingest.<dtype>= with publisher
   confirmation, or the maintained contracted HTTP publisher.
6. Persistence/read-back: retrieve emitted document IDs through registry-backed
   read operations, then verify indexing separately if your workflow needs search.

Only after required outputs are confirmed should the worker ACK the input. A
provider timeout or publish failure must follow its retry/NACK policy, not be
hidden as success. Keep source/evidence references; a username-check result is
not proof that accounts belong to the same person.

* 8. Plugins, JSONL utilities and customization

Common Lisp plugins are loaded into the server's trusted init/ASDF environment;
do not launch another standalone host for each =sa-*= command. Build/test them in
the authorized fleet environment, make the ASDF system available to the server,
then load it through the documented init lifecycle. Restart only under your
deployment procedure. A file on your host is not automatically in the server image.

Document-stream utilities accept JSONL instead of a selector. Inspect
=sa-watchlist --help= and =sa-username-targets --help=; provide validated rules
and =--target-actor= where required. Their output is data, not an instruction to
automatically execute every emitted target.

When adding an actor, update its manifest, exactly one executable, shared
continuous registration and focused conformance tests together. Reuse the shared
transport and server scheduler; do not invent another queue owner or control plane.

* Troubleshooting and safe shutdown

- Request JSON but no work: offline emission is expected without =--server=.
- Accepted target but idle worker: check registration, identity, broker/vhost,
  routing and eligible target state before retrying.
- Provider error: verify its credentials and rate limits; a server key does not
  authenticate to a third-party provider.
- Schema failure: check the actor's canonical/compatibility boundary and lock.
- Duplicate work: inspect request IDs and server lease/retry state; do not add
  an actor-owned scheduler as a workaround.

Stop the worker gracefully with Ctrl-C or its supervisor. Ending a worker does
not cancel recurring targets stored on the server. Inspect and stop those through
the registry-backed target controls, then verify no future dispatch is expected.
Revoke temporary keys and remove temporary provider sessions when finished.
