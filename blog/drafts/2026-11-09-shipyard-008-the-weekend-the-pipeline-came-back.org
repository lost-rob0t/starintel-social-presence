* Recurring targets that actually recur

Saturday's repair report opens with an uncomfortable finding: of the recurring collection targets on record, 444 had never fired again after their first acceptance. The scheduler's timer wheel drops timers beyond a ten-second span, a known open issue, and nothing existed to drive the recurring cohort.

The fix was a small driver on the collection host rather than another server patch. It enumerates recurring targets from the database every five minutes, fires the most overdue identities first as one-shot dispatches with fresh idempotency keys, and caps each run at 25 firings so recovery cannot stampede the queue. Identities that need the browser collector are gated on a live health probe, so a dead collector means skipped firings, not lost ones. The r/all discovery target now fires every 300 seconds, and the report shows its discovery documents arriving with timestamps that match the fire schedule.

Nine workers with dead event streams were restarted along the way, and a new server issue was filed for bounded queueing on the browser lane. The driver's canonical copy is tracked in the operator workspace at =tools/target-cadence-pulse.py=.

* A storage stall, recovered with the metadata intact

The same day, the collection host's USB storage enclosure stalled: thirty in-flight I/O requests and zero completions, which froze the stack's processes in uninterruptible waits and took the public ingest endpoint offline with a 502.

The recovery sequence is worth keeping. A USB port reset re-enumerated the enclosure as a new device and errored out the stuck writes. The thin-provisioning pool's metadata passed =thin_check= with a consistent verdict, so the pool was reactivated rather than rebuilt. Filesystem checks on all three volumes found only count drift. The last piece was the message broker, whose unclean crash left it listening on the network but not serving; one restart brought the server healthy on its next cycle. A minute of database sequence numbers settled the question of liveness: roughly 4,982 writes per minute at verification time.

The report closes with an honest hazard note: that USB bridge model has stalled under sustained load before, and the durable fix is moving the volume group to SATA or NVMe backing storage. That migration has not happened yet.
