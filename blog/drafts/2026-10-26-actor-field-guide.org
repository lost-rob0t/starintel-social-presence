An actor is a worker with a particular job and an explicit message boundary. In StarIntel, that job might be collecting a page, checking a username, evaluating a document against a watch rule, or maintaining a query projection. Giving those jobs names makes it possible to ask what each worker accepts and what it actually produces.

This guide introduces the capabilities verified in the maintained actor manifest registry and the related server and projection documentation inspected on October 26. It is a scoped inventory, not a claim that every actor in every StarIntel repository has been audited. The 20 manifest entries below are only one part of the actor landscape. Server services, a document-to-Prolog projection worker, and proposed orchestration roles need their own descriptions and maturity labels.

The examples are fictional task descriptions. They were not executed while writing this article.

* Reading the inventory

A declared capability means a manifest and implementation describe that operation. It does not establish that a live provider works today, that every output uses the current canonical contract, or that the full producer-to-server-to-client path has passed.

Three service arrangements appear in the registry. Target workers receive a request naming the actor and its subject. Document-stream workers consume documents already moving through the system. Server plugins run inside the server's actor host. The server owns recurring work and dispatch; an actor's continuous availability does not give it a separate scheduling authority.

Several manifest output names still describe retained legacy formats. The tables deliberately use readable output descriptions rather than suggesting that those formats are all interchangeable with canonical documents.

These workers need different standards of interpretation. A generated username is a hypothesis. A successful provider lookup is an observation. A report is derived analysis whose claims still need support. Combining them must preserve those distinctions.

These are routing and evaluation capabilities. They do not create source access, convert a candidate match into an identity claim, or establish that a downstream target has completed.

* Beyond the 20-entry manifest registry

The following components explain why “20 actors tested” must not become “all actors covered.” They have different interfaces and are not additional entries in that manifest count.

| Service or role | Input and purpose | Output | Fictional example | Maturity |
|-----------------+-------------------+--------+--------------------+----------|
| Document-to-Prolog shard worker | A normalized document projection envelope, scoped to an operator-selected dataset | Preserved originals, processing receipts, and rebuildable query projections | Replay revision 1 of a fictional policy document | Implemented packaged projection worker; not yet a subscription to the canonical server change stream |
| URL extractor | Supported historical message content | Extracted URL and relation records | Extract a documentation URL from a synthetic legacy message | Retained legacy actor; canonical input is explicitly refused pending replacement |
| Pattern matcher | A document and a configured predicate | Delivery to the pattern's subscribers | Route a synthetic message matching a fixed predicate | Implemented internal matching mechanism; not an independently advertised collector |
| Target dispatcher | An accepted target and its registered destination | Delivery to the selected local or remote worker | Route one fictional collection request | Implemented server service; delivery alone does not establish durable result readback |
| Event consumer | Runtime actor-event deliveries | Processed operational events with retry or quarantine handling | Process a synthetic worker-failure event | Implemented operational service; runtime events are not observations about world events |
| Storage service actors | Typed read, insert, or delete requests | Operation results or explicit failures | Insert and read back a synthetic document | Implemented internal persistence services; these are not collection actors |

The older server username-hunt implementation is also a separate compatibility path. Its shared name must not be taken as evidence that it has the Python worker's current canonical observation contract. This guide does not recommend treating the two implementations as interchangeable.

The server's source-orchestration protocol additionally names planning, collection, geographic resolution, correlation, and projection roles. A protocol example is a vocabulary for an intended responsibility. It is not evidence that a corresponding worker is registered or runnable. Those roles remain outside this implemented inventory until a manifest, source, and execution evidence establish them.

* What the current evidence can support

The current synthetic coverage effort exercises the 20 manifest actors across multiple kinds of checks. It still records failures, blocked controls, skipped cases, and unrun service tests. It does not establish full coverage, and its results must not be extended to the additional services above.

A useful acceptance record identifies the exact worker revision, input fixture, expected output, transport path, and persisted readback. Local parsing tests, a broker confirmation, and a server round trip answer different questions. The field guide gives a reader names and boundaries; execution evidence must establish which boundary was actually crossed.
